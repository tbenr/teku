# State Diff DAG: unified diff-based beacon state storage

Date: 2026-10-22
Status: approved; builder review done 2026-10-22 (D17-D19 added from it)
Author: Enrico Del Fante (decisions), drafted with Claude

## 1. Intent

Teku rewrites the full beacon state to disk far more often than it needs to. On
mainnet a state is roughly 300 MB of SSZ. Today, in every storage mode:

- `LATEST_FINALIZED_STATE` is rewritten as a full SSZ value on every
  finalization, so about once per epoch. It is a plain key/value variable, so
  the whole value flows through the write-ahead log and memtables.
- A full hot state is written to `HOT_STATES_BY_ROOT` every 2 epochs per fork
  branch (`--Xhot-state-persistence-frequency`, default 2).
- Archive nodes additionally write a full snapshot every 2048 slots (snapshot
  mode) or a content-addressed node delta per finalized state (tree mode).

That is on the order of 100 GB per day of state writes on a prune node before
RocksDB compaction amplification. The goal is to replace all three of these
with a single store of small diffs, written once per epoch per branch, from
which the finalized anchor, hot epoch states and (for archive nodes) any
historical epoch state can be reconstructed.

Two earlier plans (March 2026) and the `ssz-diff` branch explored this. Their
useful parts are kept (level hierarchy, UInt64 delta coding, fuzz-style tests).
Their problems are addressed by design here: full-state serialization on the
write path, a fork-dependent byte offset locator, separate hot and finalized
mechanisms, and column IDs that collide with master.

## 2. Goals, non-goals, anti-goals

### Goals

1. A non-archive node writes one small diff per epoch per branch and nothing
   else for states. Finalization writes no state.
2. An archive node uses the same store with a retention policy of "keep
   everything on the finalized chain", plus coarser hierarchy levels, and
   serves historical epoch states from it.
3. Reconstruction of the finalized anchor at startup takes a bounded number of
   reads (one snapshot plus at most ~22 diffs for prune levels).
4. Correctness is checkable by hashing: every reconstructed state must have the
   state root recorded in its node.
5. The store is the foundation for a later "frozen exited validators" feature
   (phase 3) without format changes.

### Non-goals

- Per-block diffs. Mid-epoch hot states keep being regenerated by replaying at
  most one epoch of blocks from the nearest node. This can be added later as a
  second tier keyed by block root.
- Replacing the snapshot and tree archive modes. They stay as they are and may
  be deprecated later.
- Downgrade to an older Teku on a database that has used this store.
- Slot-level historical states for archive nodes beyond what block replay
  already provides.

### Anti-goals (things that would make this a failure even if it works)

- Making the storage thread slower per epoch than it is today in a way that
  delays block import. The diff must be computed from in-memory trees, never
  from a full SSZ serialization.
- A node that cannot start because a single diff is missing. Every missing or
  corrupt node must degrade to a logged error plus a recovery path, never a
  silent hole.
- Changing the semantics of the finalized anchor (`AnchorPoint`) as seen by the
  rest of the node.

## 3. Background facts the design relies on

Verified on master `77aa8f474b`:

- The finalized anchor is the post-state of the finalized checkpoint block
  `R`, i.e. the last block at or before the epoch start slot
  (`StoreTransaction.getLatestFinalized`, `AnchorPoint.create`). `R` may be
  several epochs older than the checkpoint epoch when epochs are empty.
- `StateAndBlockSummary` allows a state whose slot is later than its block,
  but the anchor is not built that way today and this design does not change
  that.
- Validators are packed 256 per `SszSuperNode` (`SszSchemaHints.sszSuperNode(8)`
  in `BeaconStateFields`), 121 bytes each, 30,976 bytes per full supernode.
  Gloas progressive lists keep the hint; lower levels of a progressive list
  may use smaller supernodes.
- `LazyBranchNode`, `TreeNodeSource`, `TreeNodeStore` and
  `AbstractSszListSchema.loadBackingNodes` already exist for the tree archive
  mode and are reusable for loading supernodes by hash.
- `StateAtSlotTask`/`checkpointStates` and `blockStates` caches exist in `Store`.
- Free hot column IDs in `V6SchemaCombined` are 10, 11 and 12 (1-9 in use;
  8 and 9 are light-client columns).
- `KvStoreColumn.create(..., containsStaticData=true)` routes values to RocksDB
  blob files (min size 100 bytes), which avoids rewriting immutable values on
  compaction. LevelDB ignores the flag.
- `--reconstruct-historic-states` replays forward from genesis one block at a
  time and calls `onReconstructedFinalizedState(state, blockRoot)` per block.

## 5. The DAG

### 5.1 Nodes

A node is the post-state of a **checkpoint block**: for epoch `E` on a branch,
the last block at or before `start_slot(E)`. One block can be the checkpoint
block of several consecutive epochs when epochs are empty; it is still one
node, keyed by the block root.

Node record (`STATE_DIFF_NODES`, key = block root):

| Field | Type | Notes |
|---|---|---|
| version | u8 | format version, now 2 (7) |
| block slot | u64 | slot of the checkpoint block |
| state root | bytes32 | hash tree root of the node state, used to verify reconstruction |
| first epoch | u64 | first epoch this block is the checkpoint block for |
| last epoch | u64 | last such epoch known at write time (updated when a later block extends it; see 5.4) |
| level | u8 | index into the configured period list; snapshots use a dedicated value |
| parent node root | bytes32 | the diff base; zero for snapshots |
| payload | bytes | diff payload, section 6 |

Nodes are immutable once written except for `last epoch`, which is only ever
raised.

The previous node on the branch (the level-1 chain) is not stored: it is the
first of the node's ancestor checkpoint blocks that has a node (5.4), resolved
when the node is written and only used to start the parent resolution (5.2).
Record version 1 stored it as `prev node root`; nothing read it after the
parent walk replaced the prev-pointer walk (decisions 27, 40), and version 2
drops it (decision 72).

### 5.2 Levels and parents

A period list `P = [p0 > p1 > ... > pk = 1]` is configured, each dividing the
previous. The level of an epoch is the index of the largest period that divides
it. The level of a node is the highest level among the epochs it serves at
write time. Fork epochs (any spec milestone transition) and the checkpoint-sync
or genesis anchor force a snapshot. A node at the coarsest level (`p0`) is
always a snapshot (reason `periodic`), so every reconstruction chain and the
retained finalized chain stay bounded instead of growing by one level-0 diff
per period.

The parent of a node at level `L` is the nearest ancestor node on the same
branch whose level is `≥ L`. In the normal case this is the node `p_L` epochs
back. With empty epochs or missing nodes the rule degrades gracefully, and
because the parent root is stored, readers never need the period list.

Reconstruction chain of a node = follow parent pointers to the first snapshot.
Bound for [256, 64, 16, 1]: 3 + 3 + 15 = 21 diffs plus one snapshot.

Parent resolution at write time: start at the previous node and follow
`parent node root` pointers (not previous-node links) until a node of level
coarser than or equal to `L` is found. Parent chains have non-increasing level
index and skip only finer nodes, so they reach the same nearest-coarser
ancestor as a prev-pointer walk would, and they stay inside retained chains:
after prune-mode retention the level-1 nodes between coarse nodes are gone, so
a prev-pointer walk would dead-end and degrade to a needless snapshot. A
snapshot node is a valid parent at every level. Each hop is one small read;
the per-level base cache (5.5) makes the common case zero reads.

### 5.3 Snapshots

A snapshot is a node whose payload is a diff against the schema's default
(empty) state tree. Every non-zero leaf is emitted; validators are emitted as
supernode references; packed UInt64 lists are emitted as delta sections against
an empty list (i.e. raw values). This keeps one writer and one reader.
Expected size on mainnet: tens of MB (balances and inactivity scores dominate),
versus ~300 MB today.

### 5.4 Write trigger

The write trigger is the one Teku already uses: importing block `B` whose
epoch is greater than its parent's epoch (`MiscHelpers.isSlotAtNthEpochBoundary`
with n = 1). Which block is the checkpoint block depends on whether `B` sits
exactly on its epoch's start slot (correction from Task 13; the first draft
keyed every epoch by the parent, which would have made nearly every mainnet
anchor a late-created node):

- If `B.slot == start_slot(epoch(B))`, `B` itself is the checkpoint block for
  `epoch(B)`: its post-state is the node, keyed by `B`'s root, and it is in
  the transaction, so it is never skipped. `B`'s parent `R` is the checkpoint
  block for the empty epochs in between, `epoch(R)+1 .. epoch(B)-1`, if any.
- If `B.slot > start_slot(epoch(B))`, `R` is the checkpoint block for
  `epoch(R)+1 .. epoch(B)`.

In both cases `R` additionally serves `epoch(R)` when `R` is itself on an
epoch start slot, which was already recorded when `R` was imported, so a
write for an existing root only raises `last epoch`. On mainnet most epochs
start with a block, so most nodes are start-slot blocks whose state is in the
transaction; the parent-keyed path covers empty first slots and empty epochs.

`StoreTransactionUpdatesFactory` (inside the store write lock, as today) looks
up `R`'s state in `blockStates` (`getBlockStateIfAvailable`) and, if absent, in
the `epochStates` cache, which deliberately keeps the pre-epoch-transition
parent state (`cacheIfEpochState`, "ADD.PRE"). It was just used to compute
`B`'s pre-state, so one of them normally has it. The factory puts
`(R, state, servedEpochs, ancestorCheckpointRoots)` into the `StorageUpdate`.
`ancestorCheckpointRoots` is computed from fork choice: walk `R`'s ancestors
collecting every block that is itself a checkpoint block (its child's epoch is
greater than its epoch), down to and including the finalized anchor root. The
writer uses the first of these that exists as a node as the previous node; this
is what makes skipped nodes (below) harmless for the level-1 chain. The
anchor always has a node (5.6), so the list always resolves. The list is short
in practice (a few entries) and bounded by the non-finality length.

If `R`'s state is in neither cache, no node is written for that epoch on that
branch, a metric is incremented and a WARN is logged. Consequences are only
longer replay for that epoch and a longer chain for later nodes, because every
pointer in the DAG is resolved against nodes that exist, never against the
block tree. The finalized anchor is never affected: see 5.6.

Gloas: the node is the post-block state, the same state the anchor carries
today. Envelopes stay in their own hot storage and are re-applied by the
existing regeneration path. A future post-envelope node kind is a format
version bump, not a redesign (D17).

If a node with root `R` already exists (empty-epoch case: a later block on the
same branch extends the served epochs), only `last epoch` is raised. If the
extended range reaches a higher level than the stored node, nothing is rewritten;
the next node at that level will simply find its parent further back.

`KvStoreDatabase.doUpdate`, on the storage thread, computes and writes the node
in the same transaction as the hot block, using the per-level base cache (5.5).

### 5.5 Per-level base cache

The DAG keeps, for every level, the most recently used nodes at that level or
coarser: their roots and state trees, three at the finest level (so that a
second checkpoint block for the same epoch after a start-slot reorg still finds
its parent) and one at each coarser level (decision 49). When a new node's
resolved parent is cached at any level, the cached tree is the diff base and
the walk starts immediately. Otherwise (fork at a coarse boundary, a parent
evicted) the parent is reconstructed from the DAG, which is the same code path
startup uses, and then cached.

Memory: cached trees share all unchanged subtrees with the live state and with
each other. The cost is the changed data between the cached base and the live
state, which for a level-256 base can approach a full state in the worst case
(balances, inactivity scores, participation and the touched validator
supernodes). Coarse levels therefore keep one entry each.

After a restart the cache holds the finalized anchor, reconstructed when the
store is loaded; the rest fills lazily. A reconstruction, for a diff base or a
read, stops at the first node below the requested one whose state is cached (or
was written in the running transaction) and applies only the links above it.

### 5.6 Finalization

When the finalized checkpoint advances to `(E, R)`, the anchor state is the
state of block `R`, exactly as today. The node with root `R` already exists
(5.4). If it does not (its state was not cached at write time), the finalized
update carries the anchor state anyway (`FinalizedChainData.latestFinalizedState`)
and the writer creates the node then, as a diff against the best available
parent or as a snapshot if no parent can be resolved. So the anchor node always
exists after a finalization transaction commits. Such a late node is written at
the finest level whatever its epoch, so its parent is its previous node and its
chain contains every node that nodes written after it may already depend on;
coarse nodes written later walk past it through parent pointers. If the
anchor's chain, or the previous anchor's, cannot be loaded, the writer logs the
chain at ERROR, rewrites the anchor node as a snapshot of the carried anchor
state (`anchor_repaired`) and retains against it, instead of failing every
retry and restart.

`LATEST_FINALIZED_STATE` is no longer written. `FINALIZED_CHECKPOINT` already
names the anchor node.

### 5.7 Reading

`Database.getHotState(root)` returns the reconstructed node state when `root`
is a node, falling back to the legacy `HOT_STATES_BY_ROOT` column for roots
written before migration. `Store` regeneration (`createStateGenerationTask`)
is changed to capture the nearest ancestor that is a checkpoint block as the
persisted base: a block is a checkpoint block iff it sits on an epoch start
slot, or its child on the walked chain is in a later epoch. Everything
downstream (`StateRegenerationBaseSelector`, `StateGenerationTask`) is unchanged.

`KvStoreDatabase.createMemoryStore` reconstructs the anchor node instead of
reading `LATEST_FINALIZED_STATE`.

Reconstruction of node `N`: load its chain, materialize the snapshot by
applying its payload to the default tree, then apply each diff payload in order
with `TreeUpdates`. When a node of the chain below `N` has its state in the
base cache (5.5), the chain is loaded only down to it and the payloads above it
are applied to its tree instead; `N`'s own payload is always applied. Delta sections compose additively (each link's delta entries are
decompressed when its payload is decoded, 6.2), so they are folded along
the chain into one value array per field (the snapshot's starting from the
empty default list) and each delta field is built once after the last link,
instead of once per link (decision 40); every link of a chain has its
snapshot's milestone, and a link from another milestone is a verification
failure. After the last apply, compare the tree's hash tree root with
the node's recorded state root; a mismatch is a hard error with the chain
listed. Reconstruction runs on the storage thread like other reads and returns
through the existing async channel.

Supernodes are content-addressed, so each is rebuilt with its store key as its
known hash tree root and the root check does not rehash it; the supernodes of a
link are loaded in one batched read (RocksDB `multiGet`). The root check
therefore does not see a supernode whose content no longer matches its key:
RocksDB block checksums cover bit rot, and `verify-state-diffs` hashes the
content of every referenced supernode against its key. The applier is one per
milestone and takes the supernode source (the committed or the transaction
reader) per application.

### 5.8 Retention and pruning

Orphaned fork nodes: when hot blocks are pruned at finalization (existing
`deleteHotBlock` path), nodes with the same roots are deleted and their
supernode references released.

Prune mode, finalized chain: let `A` be the new anchor node and `A'` the
previous one. Garbage after this finalization is

    (chain(A') ∪ nodes on the branch between A' exclusive and A inclusive) \ chain(A)

where `chain(x)` is the reconstruction chain of `x`. Nodes between `A'` and `A`
are the just-finalized canonical block roots, which the finalization update
already carries (`finalizedChildToParentMap`); those that have a node are the
candidates. (An earlier draft walked previous-node pointers from `A`; that misses
nodes when the anchor node itself was created late, decision 29.) Each
finalization therefore touches a handful of nodes. Steady state on disk is one
snapshot, at most 3 L64, 3 L16, 15 L1 nodes and the hot nodes above the anchor.
When a new snapshot enters the chain the entire older chain becomes garbage in
one step.

Archive mode: nothing on the finalized chain is deleted, unless a retention
window is configured (5.11, "Retention window"). Orphan pruning is the same as
prune mode.

`HOT_STATES_BY_ROOT` entries written before migration are deleted by the
existing hot-state pruning and are not recreated.

### 5.9 Supernode column and reference counting

`STATE_SUPERNODES` (key = supernode hash, value = raw supernode SSZ bytes,
immutable) and `STATE_SUPERNODE_REFCOUNTS` (key = supernode hash, value =
u64 count, small and mutable). Keeping the count out of the 31 KB value means
a count change never rewrites the bytes, which matters for blob-file garbage
collection. A node payload references a supernode by hash; the writer, in the
same transaction, inserts the bytes when absent and increments the count.
Deleting a node decrements every supernode it references and removes both
entries when the count reaches zero. Multiple increments of the same key
within one transaction are accumulated in memory and written once.

Only whole references are stored and counted. A changed supernode that a diff
patches (6.2, decision 69) is carried inline in the payload and adds nothing
to either column; a whole reference is written when the patch would not be
smaller, when the base holds no non-empty supernode there (snapshots, a
supernode the list grows into) or when the supernode shrank.

Snapshots reference every supernode of their state and the retention rules
always keep a complete chain for every retained node, so the column contains
every supernode of every retained snapshot, but not the supernodes a diff of
a retained chain patched since. Phase 3 freezes only supernodes whose hash is
in the column (9).

### 5.10 Bootstrap, flag and mode marker

On startup with `--Xdata-storage-state-diffs` and no `STATE_DIFF_MODE` marker
variable: read `LATEST_FINALIZED_STATE` and `FINALIZED_CHECKPOINT`, write a
snapshot node for the checkpoint root (served epoch = checkpoint epoch), set
the marker, delete `LATEST_FINALIZED_STATE`, all in one transaction. From then
on the marker, not the flag, selects the behaviour; starting without the flag
on a marked database logs at INFO that diffs remain in use. Fresh databases
created with the flag write the genesis or checkpoint-sync anchor as a snapshot
node in `storeInitialAnchor`.

`--Xhot-state-persistence-frequency` and `--data-storage-archive-frequency` are
ignored when the store is active; a WARN is logged if they are set.

### 5.11 Archive specifics

Level configuration: `--Xdata-storage-state-diff-archive-levels`, a list of
epoch periods that must each divide the previous and whose last entry must be
256 (the prune list is appended). Default `65536,8192,2048`. Changing it on an
existing database is safe: a new coarse node whose required parent does not
exist is written as a snapshot.

Historical reads: `getLatestAvailableFinalizedState(maxSlot)` finds the
checkpoint block root for `epoch(maxSlot)` via the finalized block-by-slot
index (floor lookup at the epoch start slot), reconstructs that node and
returns it. `StateCacheLoader` then replays finalized blocks to the requested
slot as today. If that checkpoint block has no node (a skipped node, 5.4), the
previous checkpoint block's node is used, down to the window start, and then
the one checkpoint block before the start epoch's: when the start epoch's own
node was skipped, the oldest retained node lies there (decision 62). A
reconstruction failure is an error for the caller, not an empty result.
Epochs before the window start are not served.

Implemented (phase 2, first slice, decision 51): the first served epoch is a
hot variable, `STATE_DIFF_WINDOW_START` (14), written with the anchor snapshot
when an archive database switches to state diff storage or is created with it
(the anchor's epoch), and moved by the retention window.
`Database.getEarliestAvailableFinalizedStateSlot` reports the start slot of
that epoch (the spec draft said "the slot of the earliest snapshot node"; the
window start is what reads honour). An archive database without the variable
(switched from prune mode, or to state diff storage before this slice) records
the previous anchor's epoch at its next finalization: before it only the
anchor chain was kept. Finalized states are no longer written to the legacy
finalized state columns in this mode; the state-root-to-slot index
(`addFinalizedStateRoot`) is still written for every finalized state the update
has at hand, as before, and the legacy `StatePruner` is not started.

`--reconstruct-historic-states`: the service calls
`onReconstructedFinalizedState(state, blockRoot)` for every block in order from
genesis. The writer accepts a state as a node when the block is a checkpoint
block, decided by checking whether the next finalized block (floor lookup on
the block-by-slot index) is in a later epoch. The genesis state is written as a
snapshot. Because states arrive in increasing epoch order, every level's parent
exists when needed and the per-level base cache applies. The service also
drives `StateRootRecorder` through `getLatestAvailableFinalizedState(slot - 1)`
per block today; in diff mode the writer must keep the previously reconstructed
state in memory for that call rather than reconstructing a node per block.
Until this is implemented, the configuration rejects
`--reconstruct-historic-states` when state diff storage is requested by the
flag (decision 62); a database in state diff mode by its marker alone is not
known at configuration time.

Pre-migration history on an existing archive node is not served from the
legacy snapshot or tree columns (D19); `getEarliestAvailableFinalizedStateSlot`
reports the earliest snapshot node.

Reconstruction chain bound with the archive levels: one snapshot plus at most
7 + 3 + 7 + 3 + 3 + 15 = 38 diffs, independent of how old the target epoch is.
Reading a stored historical state never replays blocks beyond the target
epoch; only producing states the database never had (backfill) replays from
an older state forward.

**Retention window (phase 2, first slice).** Between prune mode (keep only
the anchor's chain) and archive mode (keep everything) sits a bounded window:
keep every canonical node of the last W epochs plus the reconstruction chain
of the oldest node in the window. That chain is sufficient for the whole
window, because every node inside the window resolves its coarse parents to
the nearest coarser node below the window boundary, which the oldest node's
chain passes through; so the "backbone" below the boundary is at most one
chain of nodes. Garbage at each finalization is the existing prune rule with
the anchor replaced by the oldest retained node: the node that just left the
window unless it is on the new backbone, plus the old backbone minus the new
one. `--Xdata-storage-archive-finalized-states-retained` (slots) already
expresses this retention and is reused: `W = retained / slots_per_epoch`
epochs, the window start being `anchor_epoch - W`; 0 (the default) keeps the
archive unbounded. `getEarliestAvailableFinalizedStateSlot` reports the
window start and the snapshot-mode state pruner is not used. History begins
at the switch or at the checkpoint-sync anchor; no genesis backfill is needed.

As implemented (decision 51): the oldest retained node `O` is the node of the
checkpoint block of the window start epoch `S`, or the latest earlier
checkpoint block's node when that one was skipped. At a finalization that
moves `S` from `S'` to `S`, the candidates are `chain(O')` and the checkpoint
block roots of the epochs `S'..S` (floor lookups on the finalized blocks, which
the update writes first); everything in `chain(O)` is removed from them and the
rest deleted. The window start moves by at most 256 epochs per finalization,
so a backlog (a lowered `W`, or an unbounded database given a window) is
drained in bounded steps, logged at INFO. A raised `W` does not move the start
back: deleted history does not return. When no checkpoint root from `S'` to
`S` has a node, or `chain(O)` cannot be loaded (ERROR), nothing is deleted and
the start stays, to be retried at the next finalization; the anchor is not
repaired for it. The start is persisted in `STATE_DIFF_WINDOW_START` and
published as `storage_state_diff_window_start_epoch`.

**Reconstruction anchor (phase 2).** A fresh node that wants states older
than its checkpoint anchor must produce them by replaying blocks forward, and
today that replay starts at genesis. An operator can instead supply an older
finalized state (`--Xreconstruct-historic-states-from=<file or URL>`, the same
shape as `--initial-state`, or an admin API accepting the SSZ; an archive
node's `/eth/v2/debug/beacon/states/{slot}` is a natural source). The
historical block sync lowers its backfill target to that state's slot when it
is older than the default target; once the backfill reaches it, the supplied
state's hash tree root is checked against the state root carried by the block
at that slot, which ties it to the checkpoint-anchored chain without added
trust; reconstruction then replays forward from it to the checkpoint anchor,
writing one node per epoch (the first as a snapshot), and the two chains meet
at the anchor's existing node. Peers are only required to serve blocks for
`MIN_EPOCHS_FOR_BLOCK_REQUESTS`; an older anchor only logs a warning at
startup, and the backfill keeps retrying until peers that serve those blocks
are found (public archives or the operator's own nodes), as the historical
block sync already does when data is missing.

`--data-storage-mode archive` with the flag selects this archive; without the
flag the snapshot or tree archive is used as today.

## 6. Diff payload and tree walk

### 6.1 Walk

`StateTreeDiffer.diff(BeaconStateSchema schema, TreeNode base, TreeNode target)`
walks the two trees schema-guided from the state container down:

- For each container field, compare child roots; skip equal ones.
- For fields configured as **delta fields** (balances, inactivity scores; found
  by field name through the schema at that slot), read both packed UInt64
  lists and emit a delta section.
- For all other subtrees, recurse comparing hashes. At a leaf, emit the leaf.
  At an `SszSuperNode`, emit a patch of its changed and appended elements when
  the base holds a non-empty supernode of the same depth there and the patch
  is smaller than a whole reference (6.2); otherwise emit a supernode
  reference (and store the supernode bytes). At a subtree whose target root is the zero root for its depth, emit a
  "zeroed subtree" entry instead of descending (list shrink).
- List length leaves are ordinary leaves.

Hashes are already cached on both trees (both states have been hashed by block
processing), so the walk touches only changed paths.

Correction found during implementation (Task 4): in Teku a `LeafNode`'s data
length is semantically significant even though hashing zero-pads it. Appending
a zero element to a byte list keeps the chunk's root but lengthens the leaf's
data, and element reads and serialization then depend on that length. So equal
roots do not imply equal trees. The walker therefore skips a subtree only when
base and target are the same node instance (the common case, since Teku's
`TreeUpdates` shares untouched subtrees by reference); for different instances
with equal roots it descends without hashing and emits only leaves whose data
length differs; for different roots it descends hash-guided as before. After a
restart the reconstructed base shares no instances with the live state, so the
first node per level pays one hash-free full walk. For the same reason a
`ZeroedEntry` is emitted only when the target subtree is data-equivalent to the
canonical zero tree; a zero-filled participation list after an epoch reset is
emitted as leaves (about 1 MB raw per epoch, which the database's LZ4 collapses).

Base and target must be the same milestone. Across a fork the writer forces a
snapshot (5.2).

### 6.2 Payload sections

All integers are unsigned LEB128 varints unless stated; gIndexes within a
section are sorted and delta-coded.

1. `LEAVES`: count, then (gIndex delta, length, bytes). Length 32 for packed
   leaves, variable for small `LeafDataNode`s.
2. `SUPERNODES`: for each list field with supernodes: field index, count, then
   (gIndex delta, depth, hash32). The applier obtains the `SszNodeTemplate` from the
   field's list schema.
3. `PATCHES` (decisions 69, 73): for each list field with patched supernodes:
   field index, count, then per patch (gIndex delta, depth, element size,
   element count, written count, the written element indices as gaps from the
   previous index plus one, then the written elements back to back). The
   applier reads the supernode at the gIndex of the base tree, which must be
   a supernode of that depth with at most the element count, copies its
   bytes extended with zeros to the element count, writes the elements and
   builds a plain supernode whose root is computed from its content, so the
   state root check covers it. The element size must be the field template's.
   Patches are applied link by link in a chain application, like the other
   non-delta sections. The differ patches when the written elements, their
   index gaps, the element size and the two counts take fewer bytes than a
   whole reference's 32-byte hash plus the supernode's content (decision 70);
   the codec owns that cost (`patchEntryBytes`, `patchElementBytes`).
4. `ZEROED`: count, then gIndex deltas of subtrees to replace with the zero tree
   of the matching depth.
5. `COPIED`: count, then (target gIndex, source gIndex) of subtrees equal to
   another field of the base (participation rotation).
6. `DELTA`: for each delta field: field index, raw length, compressed length,
   then the field's delta block compressed as one zstd frame (payload version
   2, decision 63). The raw block is base count, target count, then zigzag
   varint deltas for `min(base, target)` elements and raw values for appended
   elements. Shrinking is supported (deltas for the surviving prefix). A
   reader checks the raw length against the frame header's content size and
   against the frame size (zstd expands at most 32768x) before allocating.

The applier groups entries by tree depth, because `TreeUpdates` rejects mixed
depths (`getDepthAndValidate`), and applies one `TreeUpdates` per depth in
order from deepest to shallowest, or uses `updated(gIndex, node)` per entry for
small sections. For delta sections it rebuilds the list's packed leaf subtree
from the resulting long array, once per field and reconstruction chain since
the deltas of a chain are folded first (5.7). Packed uint64 lists are read and
built at chunk level (4 little-endian values per 32-byte leaf), never boxing an
element; bounded lists get a balanced data tree of the schema's depth,
progressive (Gloas) lists go through
`ListSchemaUtil.createPackedProgressiveListTree`, and both produce the hash
tree root and SSZ of `createTreeFromElements`.

The format is versioned per node (a leading version byte, now 2); adding
sections or changing an encoding is a new version. (The `PATCHES` section was
added to version 2 in place, and changed in place to a per-entry element size,
before any version 2 database outside soak copies existed.) Version 1 (the
same layout with uncompressed delta blocks) is not read. The database-level
format gate is the `STATE_DIFF_MODE` marker (section 7, decision 73): a
database marked 1 holds version 1 records and payloads and is rejected when it
is opened, with a message to re-sync into a fresh data directory, so the
codecs know only their current version and report any other one as unknown.
Later versions should keep reading older ones once the format is no longer
experimental.

The encoder writes into one buffer sized for the worst case, after room for
the node record header, compresses each delta block straight into it and trims
it once; the record codec then writes its header into the reserved room, so the
trim is the only copy (decision 73). It reports the bytes each section takes,
which the section metrics publish. The delta codec sizes its output exactly in
a first pass. The decoder reads the payload in place, also inside a node
record (`TreeDiffCodec.payloadView`): leaf data and patch elements are views
(tree leaves and patched supernodes copy them), supernode and zero roots are
copied, delta blocks are decompressed straight from the payload by one
decompressor per read (decision 68, 73). A chain application folds each delta
block over its pending values in place (decision 73).

### 6.3 Expected sizes (to be measured, see 10)

Per-epoch diff on mainnet: balances and inactivity deltas dominate. The hackmd
measured 35 KB gzip for 400k validators' balance deltas; under LZ4 at the DB
level the ratio will be worse. Budget: a few MB per epoch before DB
compression. If measurements show the delta section compresses poorly under
LZ4, application-level compression of that section alone is an isolated
change behind the format version.

Measured (decision 61, window soak): balances 3.9 MB raw per node, every node;
inactivity scores 2.4 MB raw on one node in four; nodes 1.47 MiB on disk
against 5.35 MB raw under RocksDB LZ4, uncompressed at the bottom-most level.
Payload version 2 compresses each delta block with zstd (decision 63): on a
synthetic mainnet-like node (2M balances, 12k leaves) the payload drops from
6.4 MB to 1.4 MB, balances 4.0 MB to 1.0 MB (4.0x), a 2M-element inactivity
block of zeros to 212 bytes, for about 17 ms of compression and 6 ms of
decompression per node. The ratio on real data is read off
`section_bytes_total{section=deltas|deltas_compressed}`.

Supernode patches (decisions 69-71): on a synthetic node with 25 changed
supernodes (20 with one changed validator, 4 with three, 1 with ten) and 4
deposits into the last supernode, the supernode cost of the node drops from
787,872 bytes (888 bytes of references in the payload plus 786,984 bytes of
content for the supernode column) to a 5,757-byte patch section and nothing in
the column; on a random 8192-validator Electra state with 6 validators changed
in 5 supernodes, from 155,057 bytes to 767. Applying the 26 patches and
hashing the result takes 5.2 ms against 0.08 ms for the whole references,
whose roots are known: about 0.2 ms per patched supernode left in the final
tree of a reconstruction.

## 7. Storage layout

| Column / variable | ID | Key | Value | Static data |
|---|---|---|---|---|
| `STATE_DIFF_NODES` | hot column 14 | block root | node record (5.1), header version 2 | yes |
| `STATE_SUPERNODES` | hot column 15 | supernode hash | supernode SSZ bytes | yes |
| `STATE_SUPERNODE_REFCOUNTS` | hot column 13 | supernode hash | u64 reference count | no |
| `STATE_DIFF_MODE` | hot variable 13 | - | marker = format version, now `02` | - |
| `STATE_DIFF_WINDOW_START` | hot variable 14 | - | u64 epoch: first finalized epoch an archive database serves (5.11) | - |

Node record layout, version 2: `u8 version`, `u64 block slot`, `bytes32 state
root`, `u64 first epoch`, `u64 last epoch`, `u8 level`, `u8 snapshot`,
`bytes32 parent node root`, then the payload (6.2); integers big-endian, a
fixed 91-byte header so `last epoch` is rewritten in place. Version 1 had a
32-byte `prev node root` before the parent root (decision 72).

The `STATE_DIFF_MODE` marker is the format gate (decision 73): this build
writes `02` and opens only a database marked `02`. A database marked `01`,
written by an earlier experimental build with version 1 records and payloads,
fails to open with an unrecoverable error asking to re-sync into a fresh data
directory, and so does `verify-state-diffs`; any other marker fails as an
unknown format. The codecs carry no version 1 branches.

Both backends get the columns through `V6SchemaCombined`, so every V6 variant
(snapshot, tree, and both RocksDB and LevelDB) carries them; they stay empty
until the marker is set. `SchemaHotAdapter` exposes them. `LATEST_FINALIZED_STATE`
(variable 5) remains declared for bootstrap and legacy reads.

An earlier draft had a separate snapshot column; it is unnecessary because
snapshots use the node format. The static-data flag places large values in
blob files only when `--Xdata-storage-rocksdb-blob-db-enabled` is on (default
off); with the default, snapshots live in SSTs and get rewritten by
compaction, which for one snapshot per 256 epochs is acceptable (D18).

## 8. Write path, read path and store integration summary

Write (per imported first-block-of-epoch `B`, storage thread):

1. `StorageUpdate` carries `(R, stateR, servedEpochs, prevNodeRoot)`.
2. Resolve level and parent (5.2, 5.5).
3. Walk base vs `stateR` tree (6.1), producing payload and supernode set.
4. In the hot transaction: put node record, upsert supernode refcounts.
5. Update the per-level base cache with `stateR`.

Finalization (storage thread, same transaction as today's finalized update):

1. Ensure the anchor node exists (5.6).
2. Compute garbage (5.8) and delete nodes and supernode references.
3. Do not write `LATEST_FINALIZED_STATE`.

Read:

- `getHotState(root)` → reconstruct node (5.7).
- `createMemoryStore` → reconstruct anchor node.
- Archive: `getLatestAvailableFinalizedState(slot)` → node for the epoch (5.11).

Store changes are limited to: selecting every epoch boundary, passing the
checkpoint-block state and `prevNodeRoot` in the update, and using the
checkpoint block as the regeneration base. No new provider interface is
needed; the existing `stateProvider` channel reaches the DAG through
`getHotState`.

## 9. Phase 3: frozen exited-validator supernodes

Not part of the first two phases; the store is designed so this needs no
format change. It was built and measured as an exploratory attempt on
2026-10-29 (branch `worktree-state-diff-tier3`, decisions log entry 77, report
`.superpowers/sdd/2026-10-29-state-diff-tier3/tier3-attempt-report.md`). The
design below is what was built; 9.2 to 9.6 record what the attempt taught and
why it is not pursued in this form.

### 9.1 Design as built

**Unit.** A `FrozenSuperNode` implements `TreeNode` and `LeafDataNode`, holding
the supernode hash, depth, element count, the `SszNodeTemplate` and a loader
against `STATE_SUPERNODES`. `hashTreeRoot` returns the stored hash. `get(i)`
loads the bytes on demand, memoized through a `SoftReference`. `updated()`
loads and delegates to a real `SszSuperNode`, exactly as `LazyBranchNode`
does, so any write thaws it. `getData()` loads. `iterate` passes itself as a
single node, like `SszSuperNode` does, so tree iteration does not descend.
`FrozenRanges` maps the frozen supernodes of a list to element index ranges by
a binary search over the schema's element gIndices, which works for bounded
and progressive (Gloas) lists alike.

**Freeze policy.** A `SupernodeFreezer` hook in `TreeDiffApplier` decides, for
every whole supernode reference a reconstruction places, whether to keep the
content or a frozen node; the applier stays ignorant of validators. The
storage-side `ExitedValidatorFreezer` freezes a validators supernode when
every element has `effective_balance == 0`, `activation_epoch` set,
`exit_epoch < E` and `withdrawable_epoch <= E`, with `E` the epoch of the node
reconstructed (the two epoch conditions make every canned status fact below
checkable on the bytes rather than assumed from spec invariants; they exclude
no validator on mainnet). Eligibility is memoized by hash. Freezing happens
only in `reconstruct` and `reconstructAndCache`, behind the hidden flag
`--Xdata-storage-state-diffs-freeze-exited`; states derived from a
reconstructed tree by `updated()` keep the frozen nodes. Patches are inline
and never freeze (their content is not in `STATE_SUPERNODES`). The differ
compares frozen nodes by root, depth and size without loading, and the
transaction's supernode sink is lazy, so the write path, snapshots included,
loads nothing. A patch over a frozen base loads it.

**Why materialize-on-write is required.** Two fields of a withdrawn validator
can still change: `withdrawal_credentials` via a BLS-to-execution change (no
activity check in `BlockProcessorCapella.processBlsToExecutionChanges`), and
`effective_balance` after an Electra deposit tops up a withdrawn validator
(`EpochProcessorElectra.processPendingDeposits` applies it as a balance
increase, and the next `processEffectiveBalanceUpdates` raises the effective
balance). Both go through `validators.set(i, ...)`, which thaws the supernode.

**Iteration fast paths** (in `ethereum/spec`, seven methods, each a no-op when
no frozen node exists in the process):

- `AbstractValidatorStatusFactory.createInitialValidatorStatuses`: a frozen
  range yields canned statuses (inactive in previous, current and next epoch,
  withdrawable, not eligible, effective balance 0; `slashed` and the
  withdrawable epoch are only read together for a validator whose withdrawable
  epoch is in the future, which cannot hold).
- `BeaconStateAccessors.getActiveValidatorIndices` on cache miss (for epochs
  from the state's previous epoch on), `processRegistryUpdates` (abstract and
  Electra) and the activation-queue filter skip frozen ranges.
- Withdrawals sweep: check `balances[i]` first; a frozen index with zero
  balance advances without loading, still counting toward
  `MAX_VALIDATORS_PER_WITHDRAWALS_SWEEP` so `next_withdrawal_validator_index`
  stays spec-equal.
- `EpochProcessorElectra.processEffectiveBalanceUpdates` reads every validator
  every epoch since Electra (the pre-Electra version only on hysteresis); a
  frozen validator is read only when its balance exceeds the upward threshold,
  the thaw case.
- REST validator queries and full-state SSZ serialization load; slower but
  correct.

**Equivalence tests.** Each fast path has a test running the same epoch
transition with and without freezing, comparing state roots and asserting
zero loads, on Electra, Fulu and Gloas.

| validators meeting the freeze rule | | 1,555,506 (65.1%) |
| wholly withdrawn depth-8 supernodes | | 1,005 of 9,334 (257,280 validators, 10.8%) |

| epoch transition, cold caches, median | 6.02 s | 5.62 s |

### 9.3 Why the gain is capped

- **Granularity, not the exit rate.** Exits are spread over the whole index
  space (62-86% of each decile up to the eighth), so a depth-8 supernode is
  wholly withdrawn only 11% of the time although 65% of validators are. The
  share of the registry in wholly withdrawn blocks by supernode depth: 10.8%
  at 8, 19.8% at 7, 30.4% at 6, 40.1% at 5, 47.7% at 4, 53.7% at 3.
- **The saving is per distinct registry copy, not per state.** Hot states, the
  anchor and the base-cache trees derived from one reconstruction share the
  frozen nodes by identity, so the 29 MB applies once or a few times, not
  once per state.
- **The cold pubkey index reloads everything.** A freshly reconstructed state
  has an empty `ValidatorIndexCache`; the first pending deposit whose pubkey
  is unknown scans the whole registry (`findIndexFromState` from
  `processPendingDeposits`), loading every frozen supernode. A frozen range
  cannot be skipped there: a top-up deposit to a withdrawn validator needs
  its index. That cache holds every validator scanned, exited included, as
  `BLSPublicKey` keys wrapping leaf slices of the supernode bytes, one
  instance per `TransitionCaches` lineage.
- **The list view cache pins the content back.** `AbstractSszComposite` keeps
  one `Validator` view per index read; each view slices the loaded supernode
  content, so after any full scan (cold pubkey lookup, cold status creation,
  REST listing) the frozen bytes are in the heap again for as long as that
  view chain lives: +1.2 GB, plain and frozen alike, forty times the saving.
- **When freezing happens.** Only on reconstruction: a checkpoint-synced node
  freezes nothing until a restart or a DAG read; supernodes patched since the
  last snapshot stay plain until a later snapshot is reconstructed.
- **Pruning hole (theoretical, not fixed).** If a retained chain reaches a
  supernode's content through a patch while the live frozen instance came
  from another chain's whole reference that is pruned before a snapshot
  re-references the hash, the bytes are deleted under a live frozen node.
  Periodic snapshots re-reference every unchanged supernode whole, so the
  normal case holds; the failure is loud (`IllegalStateException` on load).
  A real fix pins frozen hashes or forces whole references at frozen
  positions.
- **Consensus footprint.** Seven methods carry fast paths whose correctness
  rests on a byte rule enforced in storage: clean and tested, but a permanent
  coupling between `ethereum/spec` and the store, for 5-10% of an epoch
  transition that is better obtained generically (9.6).

### 9.4 A finer validators supernode

The supernode depth is a schema hint (`sszSuperNode(8)` in
`BeaconStateFields`), so coverage can be raised by halving it. Estimated
per-copy object overhead: about 144 bytes per supernode (node, `Bytes`
wrapper, array header, cached root) plus about 96 bytes per added branch
node with its cached hash.

| depth | validators per supernode | supernodes | extra objects per copy | frozen content | net saving per copy |
|---|---|---|---|---|---|
| 8 | 256 | 9.3k | 0 | 30 MB | 30 MB |
| 7 | 128 | 18.7k | 2 MB | 55 MB | 53 MB |
| 6 | 64 | 37k | 7 MB | 84 MB | 77 MB |
| 5 | 32 | 75k | 16 MB | 110 MB | 95 MB |
| 4 | 16 | 149k | 34 MB | 132 MB | 98 MB |
| 3 | 8 | 299k | 69 MB | 148 MB | 79 MB |

Depth 4 or 5 nets about 95 MB per distinct copy. Costs outside the heap are
small: a snapshot carries 8x more 32-byte references at depth 5 (about 2.4 MB
instead of 0.3 MB), the supernode and refcount columns get 8x more rows, the
diff walk visits 8x more nodes at that level; patches are per validator and
unchanged. The supernode roots differ, so it is a format marker bump and a
re-sync of DAG databases (the state root is unchanged). A likely CPU upside
independent of freezing: every validator change copies and rehashes its
supernode, 31 KB and about 2,300 hashes at depth 8 against 3.9 KB and about
290 at depth 5, and the effective-balance changes of an epoch transition are
scattered across supernodes. Both effects are a one-line experiment with the
harness in plain mode; not run yet.

### 9.5 What other clients do (surveyed 2026-10-29)

No client freezes, offloads or skips exited validators in memory or in epoch
processing; all iterate the whole registry and skip only rewards and
inactivity by eligibility, as Teku does. Their levers: a compact per-validator
representation (Prysm's flat 128-byte `CompactValidator` since v7.1.4 saved
300-450 MB on mainnet; Lodestar keeps one node per validator), pubkeys stored
once and shared (Nimbus persists states without pubkeys since 2021; Grandine's
2026 structure-of-arrays `ValidatorList` has an append-only shared pubkey
list; Lighthouse tried an `Arc` pubkey split in 2022-23 and dropped it),
field-wise on-disk diffs where an unchanged validator costs nothing
(Lighthouse and Prysm hdiff; the DAG's content-addressed supernodes and
patches are the equivalent), and a process-wide pubkey-to-index cache
(Lodestar, Lighthouse, Grandine). Teku's 121 bytes per validator is already
the densest in-memory form. At the protocol level EIP-6914 (reuse of
withdrawn indices) is stagnant and its spec text was removed in August 2026;
nothing is scheduled; MaxEB consolidations shrink the active set, not the
registry.

### 9.6 Alternatives and recommendation

Tier 3 is not pursued in this form. In order of expected value:

1. **Share pubkeys across states.** A supernode variant holding the 73
   mutable bytes per validator and reading the 48-byte pubkey from one
   process-wide, index-ordered table for reads and hashing: 40% of the
   registry for every validator, no consensus changes, no dependence on exit
   clustering. The per-lineage `ValidatorIndexCache` already is a full,
   duplicated pubkey table and would become that shared table.
2. **Fix the cold paths first**, whatever else is chosen: a process-wide
   pubkey index so a fresh state never scans the registry, and status
   creation that reads supernode bytes instead of building 2.4M views. Both
   remove the 1.2 GB view-cache pinning and most of the cold status cost for
   every node, and are prerequisites for any freezing to keep its memory.
3. **Finer supernode depth** (4 or 5), measured first without freezing for
   its hashing and update gains, then with freezing for the ~95 MB net.
4. **Sparse supernode** (live validators' bytes plus a bitmap of frozen
   slots) to reach the 65% ceiling without changing the tree shape; the most
   code in the SSZ layer. Only if memory remains the bottleneck after 1-3.

The attempt's code stays on `worktree-state-diff-tier3` as the reference for
`FrozenSuperNode`, `FrozenRanges`, the freezer hook and the harness.

## 11. Metrics

- `storage_state_diff_node_bytes` histogram labelled by level (snapshot included)
- `storage_state_diff_write_seconds` histogram (base + walk + encode + store)
- `storage_state_diff_write_phase_seconds_total{phase=base|walk|encode|store}`:
  seconds spent in each phase of the node writes, a counter of fractional
  seconds (`base`: previous node and parent resolution and the diff base, which
  reconstructs on a base cache miss; `walk`: `TreeDiffer.diff`, the delta
  blocks' varint encoding included; `encode`: `TreeDiffCodec.encode`, delta
  compression included; `store`: node record encoding, the node put and the
  supernode bookkeeping; the supernode puts themselves happen at commit)
- `storage_state_diff_reconstruct_seconds` histogram and
  `storage_state_diff_reconstruct_chain_length`
- `storage_state_diff_reconstruct_list_builds_total`: packed uint64 lists built
  by reconstructions; one per delta field that changed along each chain, since
  the delta sections of a chain are folded before the list is built
- `storage_state_diff_base_cache_total{result=hit|miss}`
- `storage_state_diff_nodes_total{state=written|deleted|deleted_corrupt|anchor_created_late|anchor_repaired}`
  (`deleted_corrupt`: a node deleted on retention or repair whose
  record or payload could not be decoded, so its supernode references were not
  released, which also logs an ERROR; `anchor_repaired`: a finalized anchor
  rewritten as a snapshot because a chain could not be loaded or its missing
  node could not be created, which also logs an ERROR naming the trigger;
  a node written and then repaired in one update counts once as `written`)
- `storage_state_diff_snapshots_total{reason=forced|periodic|milestone|no_parent}`
  (`periodic`: a node at the coarsest level; a `no_parent` snapshot outside
  bootstrap is a regression signal and also logs a WARN)
- `storage_state_diff_section_bytes_total{section=leaves|supernodes|patches|zeroed|copied|deltas|deltas_compressed}`
  and `storage_state_diff_section_entries_total{section=...}` (same labels):
  payload of the written nodes by section, the exact bytes each section takes
  as reported by the encoder (counts, group headers, gIndexes and lengths
  included; an empty section counts its count byte), so all sections but
  `deltas` sum to the payloads less one version byte each; `deltas` counts the
  raw delta bytes before compression and `deltas_compressed` the delta section
  as stored, so the compression ratio can be read off (decision 73, which
  replaced the approximate data-only counts); a DEBUG line per node gives
  epochs, level, reason, total bytes, the section byte counts and the
  compressed delta bytes.
  (The per-field `delta_field_bytes_total{field}` and
  `delta_field_entries_total{field}` counters of the window wave were removed
  once they had sized the inactivity share, decision 66.)
- `storage_state_diff_window_start_epoch`: gauge, the first finalized epoch an
  archive database serves (5.11); absent on prune databases
- `storage_state_supernodes_total{op=inserted|incremented|deleted}` and bytes
- `storage_state_diff_verification_failures_total` (any failed
  reconstruction: state root mismatch, broken chain, corrupt record or payload,
  missing supernode). A failure for a hot node other than the anchor logs a
  rate-limited ERROR and degrades to block replay; for the anchor at startup it
  is an unrecoverable error pointing at `debug-tools db verify-state-diffs` and
  checkpoint re-sync.

Node metrics and base cache entries are recorded when the DAG transaction
commits, so a failed transaction does not count or cache its nodes.

## 13. Risks and open points

- **Write-path CPU.** The walk is estimated at tens of milliseconds per epoch;
  the delta encoding reads two 11 MB arrays. Must be measured on mainnet
  states. Mitigation if needed: compute the payload outside the transaction and
  commit only the bytes.
- **Per-level cache memory.** Worst case one full state per cached level.
  Configurable level count; reconstruct-on-miss exists anyway.
- **DB-level compression of deltas.** LZ4 may compress varint deltas worse than
  gzip did in the hackmd. Format is versioned; an application-level codec for
  the delta section is a contained change.
- **Skipped nodes.** A checkpoint-block state missing from the cache at write
  time produces a gap. The anchor is always written on finalization, so the
  gap only costs replay time. The skip counter must be watched during the soak.
- **Refcount drift.** A crash between a node write and its refcount update is
  prevented by the single transaction; a bug would leak or over-delete
  supernodes. A verification tool (`debug-db` subcommand) that recounts
  references and reports discrepancies is part of phase 1.
- **Reconstruction mismatch.** A state root mismatch, broken chain or corrupt
  node is a hard error for the finalized anchor at startup, with an
  unrecoverable error naming `debug-tools db verify-state-diffs` and checkpoint
  re-sync as the recovery path; the marker makes the mode sticky, so there is
  no silent fallback to legacy columns. For any other node it is a logged
  error and the state is regenerated by block replay; at finalization an
  anchor whose chain cannot be loaded is rewritten as a snapshot.
